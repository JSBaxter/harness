# Frontend development by screenshot loop

Proven on residual-stream-viz (2026-08-31): four visual defects found and
fixed without a human ever opening the page. The core insight: make the page
**deterministically renderable at any state**, then screenshots become both
your eyes during development and byte-comparable test artifacts.

## 1. The determinism contract (build this FIRST)

Before any visuals, give the page a test API (adapt naming per project):

```js
window.__viz = {
  ready,        // true only after document.fonts.ready AND first render
  goto(i),      // render exact state i: synchronous, clamped, no animation
  eventCount,   // how many states exist
  currentEvent, // full state object, for pixel-free assertions
}
```

Rules that make screenshots pixel-stable:
- All data from a seeded PRNG (mulberry32); ban `Math.random`/`Date.now` in
  src/ (add a grep test for this).
- `goto` never touches the animation clock; animation is cosmetic attribute
  mutation BETWEEN exact states, and every state boundary re-renders exactly
  (see the event-boundary-exact rendering ADR pattern — record one).
- Await `document.fonts.ready` before declaring ready; fonts are the #1
  source of pixel flake.
- Prefer SVG over canvas when feasible: tests can assert structure via
  `querySelectorAll` counts instead of pixels.

## 2. The iteration loop

Keep a dev helper `scripts/shot.py` (serve repo over threaded http.server on
an ephemeral port → wait for `ready` → optional `goto(i)` → screenshot,
printing any console errors). Loop:

1. Write/change code
2. `uv run python scripts/shot.py screenshots/vN.png [state]`
3. **Read the PNG with your image-capable Read tool and actually look at it**
   — check text collisions, clipping, overlap, contrast, whether the design
   communicates its idea
4. Fix the worst thing you saw; reshoot; repeat until nothing is wrong
5. Screenshot MULTIPLE states, not just the idle one — bugs live in the
   mid-animation states

`screenshots/` is gitignored; version the numbered iterations locally so you
can compare.

## 3. The test stack

uv + pytest + pytest-playwright (Chromium only) + pillow. Conftest: a
session-scoped threaded `http.server` fixture yielding base_url; viewport
pinned (e.g. 1280x800). Assertion vocabulary, cheapest first:
- **Structure**: selector counts (streams: 4, blocks: 12...) — precise, fast
- **State**: `page.evaluate` against the test API — semantic, no pixels
- **Non-blank**: `len(img.getcolors(maxcolors=1e6)) > 50` — catches render
  death without brittleness
- **Layout**: `scrollWidth/Height` vs viewport — catches overflow
- **Determinism**: two fresh browser contexts, same `goto(k)`, assert
  screenshot bytes equal — this is the license for everything else
- **No network**: request interception, assert only localhost loads
- Console errors captured and asserted empty in the smoke test

## 4. The human handoff

Commit a `docs/preview.png` regenerated BY A TEST (`goto(eventCount//2)`,
overwrite, assert valid PNG). Deterministic rendering means the file only
changes when the visuals change — so every PR diff carries an always-current
picture, and the human reviews visuals from the PR page without running
anything.

## 5. Style defaults that photograph well

Dark background; semantic palette as CSS custom properties (e.g. `--c-read`
/ `--c-write`), color-blind-safe (blue/orange, not red/green);
viewport-fixed layout (`overflow: hidden`, fixed px scene) so there is
exactly one layout to verify.
